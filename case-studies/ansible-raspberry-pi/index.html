Ansible Fleet Automation

Standardizing Administration of a 150+ Device Raspberry Pi Fleet

Executive Summary

A fleet of more than 150 Raspberry Pi devices deployed across two production facilities required ongoing maintenance, auditing, provisioning, and troubleshooting. These activities were performed manually through SSH and VNC connections on a device-by-device basis, creating significant operational overhead and increasing the risk of configuration inconsistencies.

To address these challenges, an Ansible-based automation platform was implemented using an Ubuntu Server virtual machine as a centralized control node. The solution automated routine maintenance, configuration auditing, and device preparation tasks while reducing dependency on institutional knowledge.

The implementation reduced routine maintenance activities from approximately 8-10 hours to 1-2 hours, standardized configuration management across the fleet, and transformed previously undocumented procedures into repeatable and maintainable automation workflows.

Environment Overview

The environment consists of over 150 Raspberry Pi devices deployed across two production facilities located on the same campus. Devices are used in operational workflows and require ongoing maintenance, configuration validation, and periodic replacement due to movement, misuse, or hardware failure.

The environment includes:

  • Multiple Raspberry Pi hardware revisions
  • Multiple Raspberry Pi OS versions
  • Linux-based operating systems
  • Weekly maintenance requirements
  • Frequent device replacement and reconfiguration
  • Specialized production software requiring X11

Due to the dynamic nature of the environment, devices are generally managed in groups of ten. Display-only devices are maintained as a dedicated group due to their unique operational requirements.

Problem Statement

Existing Process

Prior to automation, administrative tasks were performed manually through SSH or VNC sessions on individual devices.

Routine maintenance activities included:

  • Software updates
  • Configuration verification
  • Device troubleshooting
  • Provisioning and deployment preparation
  • Cleanup of unnecessary software packages

Each system required independent administration and validation before work could proceed to the next device.

Operational Challenges

Administrative procedures required detailed knowledge of both the operating system and the organization's software stack. Key challenges included:

  • Device management limited to a single endpoint at a time
  • Configuration procedures dependent on institutional knowledge
  • Increased likelihood of skipped or repeated steps during maintenance
  • Multiple hardware and software versions requiring special attention
  • Frequent device movement and replacement
  • Limited visibility into device configuration status

Knowledge required to maintain the environment was concentrated among a small number of personnel, creating operational risk and limiting scalability.

Business Impact

Maintenance activities were performed weekly or monthly and consumed significant technician time. A single device could require several minutes for routine maintenance or multiple hours for troubleshooting and reconfiguration. Auditing often required physical inspection of devices on the production floor, increasing labor requirements and reducing efficiency.

Project Objectives

The project was designed to achieve the following objectives:

  • Reduce manual administrative effort
  • Standardize maintenance procedures
  • Improve configuration visibility
  • Centralize device management
  • Reduce maintenance cycle duration
  • Minimize configuration inconsistencies
  • Reduce dependency on institutional knowledge
  • Create repeatable and documented operational procedures

Solution Design

Technology Selection

Ansible was selected due to its agentless architecture, strong Linux support, and ability to automate administrative tasks across multiple hardware platforms without requiring software installation on managed devices.

The platform provided several advantages:

  • Centralized administration
  • SSH-based communication
  • Repeatable automation workflows
  • Support for heterogeneous Raspberry Pi hardware
  • Secure authentication through SSH key management
  • Reduced risk of human error

Architecture

The solution consists of:

  • Ubuntu Server virtual machine acting as the Ansible control node
  • SSH-based communication with managed devices
  • Centralized playbook repository
  • Shared SSH key authentication
  • Audit log generation

By hosting Ansible on a virtual machine rather than a Raspberry Pi, the management platform became more reliable and easier to maintain.

Inventory Management

Due to the frequent movement and replacement of devices, static inventory assignments are not practical. A master list of device IP addresses is maintained and periodically scanned. Reachable devices are identified through network testing and used to generate an inventory file for playbook execution. Devices are organized into operational groups of ten to allow maintenance activities to be performed in controlled batches.

Implementation Process

Phase 1: Proof of Concept

Initial testing was performed using a headless Raspberry Pi as the Ansible control node. While functionally successful, operational concerns including hardware reliability, physical access requirements, and network management limitations made the approach unsuitable for long-term deployment.

Phase 2: Infrastructure Migration

An Ubuntu Server virtual machine was provisioned to host Ansible and serve as the centralized management platform. This eliminated dependencies on Raspberry Pi hardware while improving operational reliability.

Phase 3: Secure Access Configuration

SSH keys were generated and distributed to managed devices. This enabled passwordless authentication while avoiding the use of shared credentials and reducing administrative overhead.

Phase 4: Playbook Development

Three primary playbooks were developed:

Update Playbook

Automates routine maintenance activities including:

  • apt update
  • apt upgrade
  • apt autoclean
  • apt autoremove

The playbook ensures devices remain current while minimizing manual intervention.

Audit Playbook

Provides remote validation of device configuration. The audit process verifies critical configuration values by examining specific entries within device autostart files to confirm alignment with operational requirements. Audit results are written to administrator-defined log files for review.

Cleanup Playbook

Executed as part of the device provisioning process prior to deployment. The playbook removes:

  • Unnecessary applications
  • Unused libraries
  • Unneeded firmware packages

Storage conservation is an important consideration because production workflows rely on local spool files. Excessive storage consumption can prevent devices from processing print jobs and ultimately impact operations.

Challenges and Resolutions

Challenge 1: Raspberry Pi Control Node Reliability

Problem: The original plan involved hosting Ansible on a Raspberry Pi. Testing revealed several operational concerns:
  • Intermittent kernel panics
  • Inconsistent boot behavior
  • Dependence on physical access
  • DHCP-assigned addressing

These factors reduced reliability and complicated administration.

✓ Resolution: The control node was migrated to an Ubuntu Server virtual machine, creating a more stable and maintainable management platform.

Challenge 2: Legacy Package Management

Problem: Several devices contained outdated packages that prevented successful updates. These issues were not identified during early testing and caused playbook failures during deployment.
✓ Resolution: Playbooks were modified to account for these package scenarios and ensure updates could proceed successfully.

Challenge 3: Remote Access Compatibility

Problem: Cleanup testing revealed that removing Raspberry Pi Connect components disrupted RealVNC functionality. Investigation determined that Raspberry Pi Connect relied on Wayland and external account-based services, while the organization's software stack required X11. Because RealVNC operates through X11 and does not introduce subscription requirements, it was selected as the preferred remote access solution.
✓ Resolution: Devices were standardized on X11 before deployment. This ensured compatibility between production software, remote administration tools, and operating system configuration. The issue was subsequently eliminated from future provisioning activities.

Results and Metrics

Maintenance Automation

Routine update activities were reduced from approximately 8-10 hours to 1-2 hours.

Result: Approximately 80% reduction in maintenance effort.

Device Auditing

Auditing previously required technicians to physically inspect devices across the production floor. The process can now be completed remotely in approximately 1-2 hours.

Result: Multi-day audit activities reduced to a centralized and repeatable workflow.

Provisioning Efficiency

Cleanup activities previously required approximately 30 minutes per device. Automation reduced these activities to only a few minutes per device.

Result: Significant reduction in provisioning effort and improved deployment consistency.

Knowledge Transfer

Prior to implementation, maintenance procedures depended on a limited number of personnel with specialized knowledge. Playbooks and supporting documentation transformed these procedures into documented and repeatable operational processes.

Result: Reduced operational risk and improved maintainability.

Standardization

Maintenance activities now execute through validated automation workflows.

Result: Consistent execution reduced human error, and improved configuration uniformity across the device fleet.

Lessons Learned

This project demonstrated that meaningful operational improvements can be achieved through targeted automation of repetitive administrative tasks. Several key lessons emerged:

  • Automation does not need to be complex to provide significant value.
  • Infrastructure reliability is as important as the automation platform itself.
  • Testing is critical before implementing cleanup and optimization tasks at scale.
  • Hardware and operating system variations require validation before broad deployment.
  • Documentation and automation can effectively reduce dependency on institutional knowledge.
